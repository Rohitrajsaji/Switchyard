# ADR 0004: explicit event facts and transactional idempotency

Status: accepted MVP ingestion; SQL attribution follows in M4 and outbox/worker processing follows in M7.

Evaluation records no exposure. The application emits an exposure only after rendering a flow, then listing-completion and listing-request outcomes referencing that exposure event ID. A project/environment key with `events:write` is a trusted server-side credential. Decision IDs provide correlation, not an authenticated proof that a client rendered a flow.

MVP accepts at most 100 events and 1 MiB per batch; each normalized fact is at most 16 KiB. Application scope is checked in the ingestion transaction. All facts commit together before the API returns receipts. Insert failure or a conflicting reused ID rolls back every new fact in the batch. A lost response is safe to retry with the same IDs; the client cannot infer failure merely from an ambiguous network outcome.

The identity key is project/environment/event ID. JSON object order and equivalent decimal spellings are equal through PostgreSQL jsonb comparison. Timestamp offsets normalize to UTC and precision to microseconds, matching PostgreSQL storage. The original receipt is returned on duplicate retries, including after the event has aged beyond the lateness window. Changed data under an existing identity returns conflict. Concurrent overlapping batches process identities in sorted order to avoid reversed lock ordering; unique constraints remain the final authority.

Raw facts are immutable on update. Validation uses the reported historical flag revision and stable user ID/attributes, rather than today's configuration. Unknown run IDs and malformed schemas reject the batch. Validly shaped assignment mistakes, nonrandomized decisions, unknown revisions, events more than 24 hours late and events more than five minutes ahead of ingestion time are stored as quarantined facts. Quarantine receipts are explicitly distinguishable from accepted receipts and excluded from measurement. The five-minute future allowance tolerates modest clock skew; it is not an authorization mechanism. Sensitive attribute names and unbounded JSON numbers are rejected before storage. All demo IDs/data must remain synthetic.

Completion/request events may arrive before exposure: there is no immediate exposure foreign key. `accepted` means committed fact storage, not a counted conversion. M4 SQL attribution will require a valid referenced exposure with matching run/user/variant, anchor the earliest valid event-time exposure and deduplicate completion by user/run. This preserves raw evidence while allowing late exposure to correct attribution. It also prevents a new event ID from inflating the business conversion numerator.

There is no queue or aggregate mutation in MVP ingestion. M7 will transactionally add an outbox, publish through JetStream and make derived aggregation idempotent. Transport remains at-least-once. Retention is also implemented in M7: raw data seven days, aggregate summaries ninety days and identity receipts eight days for a seven-day replay horizon. No cleanup or rebuild of older summaries is claimed before those gates pass.
